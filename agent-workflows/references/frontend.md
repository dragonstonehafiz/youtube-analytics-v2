## API client (`src/api.ts`)

Thin `fetch` wrappers, one per backend route (see `api.md` for what each endpoint does). All go through `buildUrl(path, params?)`, which sets a query param only when its value is truthy — an empty string or `undefined` is simply omitted, not sent as `key=`.

Notable naming quirks (source of truth is the function body, not the name):

- `triggerSync(plan)`, `getSyncStatus()`, and `getSyncRuns(page, pageSize)` are the wrappers that do **not** follow the file's `fetch(...).then(r => r.json())` shape — each checks `response.ok` before parsing a body. `triggerSync(plan)` POSTs a JSON `SyncPlan` body with an explicit `Content-Type` and rejects with an `Error` built by `syncErrorMessage(response)` — which reads FastAPI's `detail` field as either a plain string (400/409) or the first entry's `msg` from a 422 validation array, falling back to the status code. `getSyncStatus()` rejects with a plain `Error` naming the status code on any non-2xx response, so an unreachable or erroring `/sync/status` never gets silently parsed into a fabricated idle-like object. `getSyncRuns(page, pageSize)` sends the snake_case `page`/`page_size` params — which count **batches**, not stage rows — and rejects with the fixed `Sync history request failed (<status>)`, built from the status code alone, never from the response body, so a backend traceback cannot reach the history UI through an error path. Every other wrapper in the file resolves regardless of status, so a failed request would otherwise surface as a successful parse of an error body.

- `getPlaylistAnalytics(id, params)` and `getPlaylistAggregatedAnalytics(id, params)` are identical — both hit `GET /analytics/playlists/{id}`. Only `getPlaylistAnalytics` is actually called (from `PlaylistAnalytics.tsx`).
- Functions taking a generic `params?: Record<string, string>` bag (`getChannelAnalytics`, `getPlaylistAnalytics`, `getChannelTrafficSources`, `getPlaylistTrafficSources`, `getTopVideosByTrafficSource`, `getPlaylistTopVideosByTrafficSource`) differ stylistically from the rest of the file, which take named positional params — both patterns exist side by side; there is no in-progress migration between them documented anywhere.
- `getTopVideosByViews(sortBy, startDate?, endDate?, contentType?, privacyStatus?, title?)` and `getPlaylistTopVideosByViews(id, sortBy, startDate?, endDate?, contentType?, privacyStatus?, title?)` take a required `TopVideoSortBy` (`'views' | 'watch_time'`) as their first optional-adjacent argument, positioned before the date/filter params. There is no default — every repository call site must pass one explicitly, so `tsc` catches an omitted sort rather than it silently defaulting. All 8 current call sites are accounted for: 6 pass the literal `'views'` (`Home.tsx` ×2, `Analytics.tsx`/`PlaylistAnalytics.tsx` seven-day sidebar effects ×2 each), 2 pass the URL-derived `topVideosSortBy` (the main `TopVideosList`-feeding effect in `Analytics.tsx` and `PlaylistAnalytics.tsx`, which can resolve to either `'views'` or `'watch_time'` depending on the `top_videos_sort_by` param). Only the main `TopVideosList`-feeding call sites pass the trailing `title` argument — the seven-day sidebar effects and `Home.tsx` omit it, keeping those datasets independent of any page filter.
- `getVideosPublished(startDate?, endDate?, contentType?, privacyStatus?, playlistId?, title?)` likewise takes `title` as a trailing optional argument, added after `playlistId`.
- `getComments(query?)`, `getVideoComments(id, query?)`, and `getPlaylistComments(id, query?)` take a single optional `CommentQuery` options object (`page`, `pageSize`, `sortBy`, `text`, `videoTitle`, `author`, `startDate`, `endDate`, `contentType`) rather than positional params — a third style in this file, chosen because the endpoints take nine filters. All three delegate to a private `fetchComments()` that checks `response.ok` before parsing, so a 404 from an unknown video or playlist rejects instead of resolving into an object with no `items`. `commentParams()` maps the camelCase options onto the snake_case query names.

## Shared libraries (`src/lib/`)

**`trafficSources.ts`**
- `formatTrafficSource(type)` — raw API enum → human label (e.g. `YT_SEARCH` → "YouTube Search"); falls back to a generic title-cased version of the raw string for unmapped types.
- `getTrafficSourceColor(type)` — fixed `Record<type, hex>` lookup of 16 explicit colors; every traffic source type keeps the same color everywhere it's rendered (table bars, chart lines, donut slices), regardless of its rank in any particular filtered view. Falls back to `TRAFFIC_SOURCE_OTHER_COLOR` (grey, `#898781`) for unmapped types.
- `aggregateTrafficSourceTotals(rows)` — sums `views`/`watch_time_minutes` per traffic source type across all rows, sorted by views descending.

**`topVideos.ts`**
- `toTopVideoShape(video: Video): TopVideo` — maps a lifetime `Video` record into the `TopVideo` shape used by ranked/carousel components (`period_views = view_count`, `period_watch_time_hours = total_watch_time_hours`, `period_earnings_sgd = total_revenue_sgd`).
- `last7Dates()` — `[start, end]` ISO dates for the rolling last-7-days window (inclusive of today).
- Used by `Analytics.tsx` and `PlaylistAnalytics.tsx`. `Home.tsx` does not import this module — it defines its own local, functionally-identical copies of both `toTopVideoShape` and a `last28Dates`-equivalent inline instead. If `topVideos.ts` or `PeriodSelect.tsx`'s date helpers change, `Home.tsx`'s inline copies won't pick up the change automatically.

**`requestState.ts`**
- `RequestState<T>` — `{ data, loading, error }` for one request-backed surface.
- `pending(data)` — the initial value for a surface whose first request is in flight.
- `track(promise, setState, isActive, errorMessage?)` — drives one surface's state from one promise, dropping a superseded completion.
- Used by every page that fetches: `Home.tsx`, `Videos.tsx`, `Playlists.tsx`, `Analytics.tsx`, `PlaylistAnalytics.tsx`, `VideoAnalytics.tsx`. `CommentsPanel.tsx` and `Sync.tsx`'s History tab keep their own hand-written equivalents, which carry the same `active`-flag guard inline. See [Async card composition](#async-card-composition).

## Async card composition

Every asynchronously populated card-style surface follows one composition, supplied by `components/AsyncCard.tsx` (+ `AsyncCard.css`). Any new component of this kind must use `AsyncCard` and provide its own loading, error, empty, and content states; request states are combined only when the component consumes multiple results (see "One request, one card" below):

- The **outer shell** is mounted from the first render and never branches away. Only the **inner state region** (`.async-card-body`) switches. A card therefore holds its place in the layout during its first load and during every later refetch, and a table's card shell is a wrapper element rather than the `<table>` itself.
- States are mutually exclusive and resolve in a fixed **loading → error → empty → content** order. Loading first is what stops a pending request from rendering an empty or error message; a resolved zero-result response is what produces the empty message.
- Loading renders a circular indicator: a `role="status"` region carrying readable copy (default `Loading...`, overridable via `loadingLabel`) plus an `aria-hidden` `.async-card-spinner` ring built from `--blue-light`/`--blue`. A `prefers-reduced-motion: reduce` rule stops the ring entirely — the visible label carries the state on its own.
- Errors render as `<p class="async-card-error" role="alert">` and empty states as `<p class="async-card-empty">`, both inside the same shell as the content they replace.
- A state region that lands in a flex or grid layout needs a colocated rule to fill it — `.video-meta-card-body` gives its state children `flex: 1`, `.video-stats-bar-grid` gives its own `grid-column: 1 / -1`. Without one the indicator sizes to its content and sits against the left edge instead of centering in the card.
- A `heading` prop renders in the shell above the state region, so a card that already identifies itself (`.section-header`) keeps that heading visible while its body loads.
- `shellRef` attaches a ref to the stable shell — used by the two charts, whose `ResizeObserver` must observe a node that never unmounts.

Three shell variants:

| `variant` | Shell | Used for |
|---|---|---|
| `card` (default) | `.async-card.card` | Content laid out inside card padding — stats bar, charts, sidebar cards, meta cards. |
| `table` | `.async-card.card.async-card--table` | Card-style tables. The shell takes over `.data-table`'s background, border, radius and shadow (scoped to `.async-card--table > .async-card-body > .table-overflow-wrap > .data-table`, so a table nested inside a row keeps its own surface). The table keeps `table-layout: fixed`, its `min-width`, and its `.table-overflow-wrap` local scrolling. Pagination sits inside this shell so it resolves with the rows it pages through. |
| `plain` | `.async-card.async-card--plain` | Content that is already a stack of cards (only `CommentsPanel`) — one outer card around N inner ones would nest two glass surfaces. The stable shell adds no box of its own; **all three** of its own states carry `.card` instead, so a card surface is on screen whenever the content is not. The error keeps its red treatment over that surface via a `.async-card--plain > .async-card-body > .async-card-error` rule, which outranks `.card` regardless of stylesheet load order. |

Per-request state is held in `RequestState<T>` from `lib/requestState.ts` — `{ data, loading, error }` — with `pending(data)` for the initial value and `track(promise, setState, isActive, errorMessage?)` to drive one surface from one promise. `track` sets loading and clears the previous error before the request, then resolves into data or an in-card error. `isActive` is the owning effect's cleanup flag, so a superseded request (a filter, sort, page or tab change mid-flight) is dropped entirely rather than clearing the newer request's indicator or replacing its results. A rejected promise's `Error.message` becomes the card's error text; `errorMessage` is the fallback for a non-`Error` rejection.

**One request, one card.** Each independently fetched dataset gets its own `RequestState`, and flags are combined only where one surface genuinely consumes two results: `AnalyticsChart` waits on analytics rows plus the published-video markers it draws, `TrafficSourceChart` on traffic rows plus those markers, and `TrafficSourceTopVideosPanel` on traffic rows plus the by-source map. Statistics, the sortable top-video table, the traffic-source table, metadata, comments, listings, Sync history, and every sidebar/Dashboard card stay independent — a page-wide loading flag would reintroduce exactly the coupling this composition removes.

Holds no request state of its own — the owning component or page passes it in. |

| `CommentsPanel.tsx` | Self-contained Comments tab used by all three Analytics pages — the one component in the codebase that fetches its own data, since the three hosts share no comment state to hand down. Outside a video scope the page's comments are grouped into one shared `.card` per video, headed by its thumbnail, title (linking to that video's own Comments tab), and comment count; a video scope renders a single `.card` holding the list. | `UploadStrip.tsx` | Shared infra used by both `AnalyticsChart` and `TrafficSourceChart`: `formatCompact()` (y-axis tick formatter: plain number <1,000, `"1.5K"`-style ≥1,000, `"1.1M"`-style ≥1,000,000), `getMarks()` (quarterly/yearly `ReferenceLine` labels — **yearly kicks in once the row set spans strictly more than 8 distinct quarters** (`quarters.size > 8`); quarterly still applies at exactly 8), `computeUploadBuckets()` (buckets `PublishedVideo[]` into pixel-width-derived groups along the chart's date range, one shared `leftPct` per bucket for both content types), and `<UploadStrip>` (renders two full-width marker rows + hover popovers). `YAXIS_WIDTH`/`CHART_RIGHT`/`BADGE_DIAMETER`/`BUCKET_CLEARANCE`/`BUCKET_WIDTH` constants also live here. `BUCKET_WIDTH` is `BADGE_DIAMETER + BUCKET_CLEARANCE` (22 + 8 = 30px) — the per-bucket pixel allocation that sizes `maxBuckets`/`bucketDays`, kept tied to the badge's own footprint so adjacent bucket badges can't overlap while still permitting as many temporal buckets as the measured width allows. Each occupied bucket is centered at its own calendar position — `(daysBetween(firstDate, bucketStart) + bucketDays / 2) / totalDays`, converted to pixels in `chartAreaWidth` — so unequal real-world gaps between uploads produce proportionally unequal marker gaps; positions are never redistributed evenly by occupied-bucket ordinal. `computeUploadBuckets()` then clamps each bucket's center so a badge's full `BADGE_DIAMETER` stays inside the plotting interval (inset by half the diameter at both edges), derived from the same measured `cardWidth`/`YAXIS_WIDTH`/`CHART_RIGHT` used for bucketing; bucket membership, inclusive date-range filtering, and content-type grouping are unaffected by this. A bucket is treated as one column — one `bucketStart`, one horizontal position, an optional Video badge and an optional Shorts badge — and only a column whose center clamping actually moved gets checked against its immediate neighbor; if their centers land closer than `BADGE_DIAMETER` (a full column-diameter apart is not a collision), the two columns merge into one: the interior neighbor's `bucketStart`/position wins, and the complete `videos` and `shorts` arrays from both columns are combined in chronological order. Collision is judged purely by column distance via the exported `collides()` (centers `< BADGE_DIAMETER` apart; exactly `BADGE_DIAMETER` apart is touching, not overlapping) — never by which row(s) hold badges, so a Video-only column and an adjacent Shorts-only column still merge if their columns overlap. This only ever fires at the range's ends: the first bucket's raw center is structurally always safely inside the clamp radius (`bucketDays / 2` converts to roughly half of `BUCKET_WIDTH`, which exceeds the radius), so only the last bucket can be pushed past the boundary, by `bucketDays`'s `Math.ceil` rounding the bucket grid slightly past the actual date range. Ordinary interior buckets, however close, are never merged. `<UploadStrip>` renders two fixed-order rows spanning the full plotting width — `.upload-row.upload-row--video` first, `.upload-row.upload-row--short` second — each containing only the buckets that have that content type; a bucket with both types places one `.upload-badge-slot` in each row at the identical `leftPct`, so its Video and Shorts badges align vertically. A bucket with only one content type renders in that row alone. State is local component state, not URL params — the plan is an ephemeral action, not a shareable filter (contrast [URL and filter state](#url-and-filter-state)). Does not reuse `PeriodSelect.tsx`, whose date-range semantics don't match sync scopes.

Polls `/sync/status` every 5s into `status: SyncStatusResponse | null`, tracking poll/refresh failures in a separate `statusUnavailable` flag rather than overwriting the last-known `status`. Polling exists **only** to protect the form: `awaitingFirstStatus` (`status === null`) and `statusUnavailable` feed into `locked` alongside `state === 'running'` and `submitting`, and `locked` is wired to the `disabled` attribute of every checkbox, selector, and the submit button. None of those states render any page-level text — there is no status banner and no terminal success/failure block, and the submit button's label is the fixed string `Sync selected` in every state. `disabled` is the only button-level lifecycle signal. All visible lifecycle feedback — the running progress message, terminal messages, and the "Status unavailable" pill — belongs to the navbar's `SyncStatus` component (`components/SyncStatus.tsx`, `.sync-status*` classes in its own `SyncStatus.css`), which is unrelated to this page and unchanged. `handleSubmit` keeps the queue-request error path (`.sync-error`, "Could not start sync"-style, from `triggerSync()` rejecting) separate from the immediate post-queue status refresh: that refresh's own failure only sets `statusUnavailable` and never populates `.sync-error`, so a successful queue submission followed by a failed refresh cannot be mistaken for a failed sync start. The full-width "Sync selected" button is disabled whenever `locked` is true or nothing is selected — the backend still rejects empty and racing submissions authoritatively.

`StagePeriodSelect` and `StageScopeSelect` are extracted as their own components purely for type safety: a type predicate cannot keep a stage narrowed to `PeriodAwareSyncStage`/`ScopeAwareSyncStage` inside a nested `onChange` arrow, so the narrowed value is passed as a prop instead.

The History tab renders server-paginated **sync batches**, newest first, via `getSyncRuns(page, HISTORY_PAGE_SIZE)` with `HISTORY_PAGE_SIZE = 25` — twenty-five batches per page, not twenty-five stage rows, so `historyTotalPages` is derived from a batch count. Grouping is done in SQL rather than over the fetched page (see `database.md`): grouping client-side would split a batch across a page boundary and show a partial rollup. It fetches only while its own tab is active — entering the tab, changing page, or reloading fetches; there is no auto-refresh while it stays open. Its request state (a single `history: HistoryState` plus `expandedBatches`) is entirely separate from the form's `status`/`statusUnavailable`/`submitting`/`error`, so a history failure can never disable or alter the manual workflow, and vice versa.

Loading is **derived, not stored**: `HistoryState` carries a `key` naming the page its data belongs to, and `historyLoading` is simply `history.key !== String(historyPage)`. A boolean flipped inside the effect would leave one committed frame — after the render that changed the page or opened the tab, before the effect ran — showing the previous page's rows, a previous error, or, on a direct `/sync?tab=history` URL, `No sync runs recorded.` against a request that had not started. Deriving it means the indicator appears in the same render that triggers the request. The effect's cleanup flips an `active` flag so a superseded response is discarded, and resets the state to `PENDING_HISTORY` so leaving the tab or changing page returns the card to its indicator rather than holding stale rows underneath a newer request. Loading, request error, empty, and populated are the four mutually exclusive states of one `AsyncCard` with `variant="table"`, which holds the history table and its pagination; the card shell is on screen from the moment the tab opens, and pagination renders only in the populated state, including for a single page where both buttons are disabled. The error state keeps the generic history message and still renders `role="alert"` — it never carries `error_message`, an id, or a response body.

The empty state keys on `historyItems.length === 0` but picks its copy from `historyTotal`: `No sync runs recorded.` only at zero, otherwise `No sync batches found on this page.` — an out-of-range page is reachable by hand-editing `history_page`, since Next disables at the last page. Neither case renders pagination or triggers a redirect.

**Parent rows** carry six columns — Started \| Status \| Stages \| Fetched \| Written \| Deleted. Every value is rendered exactly as the API sent it: `started_at`, the batch `status`, and the three counters are all computed server-side, and the page derives **none** of them. `statusLabel()` only capitalizes.

This is deliberate and load-bearing. A `running` row carries `completed_at = null` from creation until its stage finishes, so that shape describes a live stage and a stranded one identically — a client-side rule keyed on the null timestamp mislabels genuinely active work as Incomplete. Distinguishing them requires knowing no sync is in flight, which only the backend's startup sweep can establish (see `database.md`'s `mark_incomplete_sync_runs()`). `incomplete` is therefore a real stored status, not a display concept, and `SyncRunStatus` carries all four values. Do not reintroduce a timestamp-derived status here.

Batch `status` is likewise the backend's, computed by the same **failed > incomplete > running > success** precedence over the batch's stages. Parent and stage cells share `statusLabel()` and the `.sync-history-status-*` badge classes, so the collapsed row and its expanded detail cannot disagree.

**Disclosure** is local state (`expandedBatches: ReadonlySet<string>`, keyed by `batch_id`), never URL state — several batches can be open at once, and a successful page load clears the set so batches from the previous page cannot reopen under unrelated rows. Both the whole `<tr>` and a real `<button>` in the Started cell drive one shared `toggleBatch(batchId)`. The button's handler **must** call `event.stopPropagation()` first: without it the click also bubbles to the row handler, toggling twice and leaving the row visually unchanged. `Sync.test.tsx` asserts one click produces one transition, and removing the guard fails it. The button carries `aria-expanded`, `aria-controls` pointing at the detail container's `batch_id`-derived DOM id, and an `aria-label` of `Sync batch started <local time>` — which contains its visible text and never the raw UUID. The expanded detail is a sibling `<tr>`, so clicking inside it does not reach the parent row's handler.

**Expanded rows** keep the original eight stage columns — Stage \| Scope \| Status \| Started \| Completed \| Fetched \| Written \| Deleted — showing each stage's *actual* counters rather than the rollup, built from an **explicit** field list, never a spread of the run object. `sync_runs.error_message` reaches the client in the API contract but is deliberately never rendered, not even for a failed stage, and neither are `id` or `batch_id`; `Sync.test.tsx` asserts sentinel values for both never appear in the document. `stageLabel()` maps `sync_type` through the same `STAGE_ROWS` labels the form uses and falls back to the raw stored value for a stage the UI no longer offers. `scopeLabel()` prefers a non-null `year`, else labels the stored scope Incremental/All, else the shared `EMPTY_CELL` em dash. `formatTimestamp()` renders stored UTC ISO strings in the browser's locale via `toLocaleString()` and returns the em dash for a null or unparseable value — a still-running stage legitimately has `completed_at = null`.

## URL and filter state

- Filter state lives in URL search params on every page, never component state — filters survive reloads/back-forward navigation and are shareable links.
- On `Videos.tsx` and `PlaylistAnalytics.tsx`'s Videos tab, the default for `start_date`/`end_date` is `''` — an absent param and an explicit empty string mean the same thing ("all data"), so there's no ambiguity to handle.
- On `Analytics.tsx`, `VideoAnalytics.tsx`, and `PlaylistAnalytics.tsx`'s Analytics/Traffic-Sources tabs, the default is **Last 28 days** instead — which makes an *absent* param mean something different from an *explicit empty string* (Custom/all data). Reading these must use `searchParams.has(key)` to distinguish the two states, and any handler writing an empty date must call `.set(key, '')` rather than `.delete(key)` — otherwise selecting "Custom" immediately snaps back to Last 28 days on the next render.
- Filter bar order is consistent everywhere it appears: Period → From/Start → To/End \| Title (where present) \| Type (where present) \| Privacy (where present), with `.filter-bar-sep` dividers between logical groups. No Apply button anywhere — every filter change triggers a live fetch. `CommentsPanel`'s bar follows the same shape with comment-specific fields: From → To \| Comment \| Commenter \| Video \| Type \| Sort.
- `CommentsPanel`'s own state is prefixed `comments_` (`comments_page`, `comments_text`, `comments_video_title`, `comments_author`, `comments_start_date`, `comments_end_date`, `comments_content_type`, `comments_sort_by`) so it can share an Analytics URL with the Analytics, Traffic Sources, and Videos tabs without either clobbering the other's filters — the same collision-avoidance reason `PlaylistAnalytics.tsx` prefixes `analytics_*`. Its dates default to empty (all data), so unlike the Analytics tabs it needs no `.has()`/`.set('')` distinction. Any filter or sort change deletes `comments_page` rather than setting it to 1, and page 1 is likewise represented by the param's absence.
- `Sync.tsx` is query-driven for navigation state only: `tab` (`sync` or `history`; unrecognized means the default Sync tab, and an absent `tab` is normalized to `sync` on mount) and `history_page` (page 1 is the param's absence, matching `CommentsPanel`'s `comments_page`). Its stage/period selections stay in component state deliberately — the plan is a one-shot action, not a shareable filter, and switching tabs does not reset it. `history_page` is parsed through a `parsePage()` guard that accepts only finite integers ≥ 1, so a hand-edited `0`, `-2`, `1.5`, or `abc` falls back to page 1 rather than producing `NaN` or a negative offset. `history_page` counts batches. A page past the end returns no items and renders the total-aware empty copy described in the Sync page section above, with no pagination controls and no redirect. Batch expansion is deliberately **not** in the URL — it is transient view state, not a shareable filter, and is cleared on every page load.
- Every query-driven page uses `useReplaceSearchParams()` (`src/hooks/useReplaceSearchParams.ts`) instead of React Router's `useSearchParams()` directly. It wraps the same `[searchParams, setSearchParams]` pair but forces every update to `{ replace: true }`, so filter/sort/page/tab changes update the URL without growing browser history — the current pathname keeps a single history entry no matter how many query changes happen on it. Pathname navigation (`<Link>`, `TopNav`'s `navigate(to)`) is unrelated to this hook and continues to push history normally. Any new query-driven page must use this hook rather than calling `useSearchParams()` directly.

## Tests

Component tests live in `frontend/tests/`, **not** beside the code they exercise, and are named `<Subject>.test.tsx`. They run on Vitest with `@testing-library/react` and `jsdom`, all three development-only dependencies. `npm test` (`vitest run`) runs the suite; a single file runs via `npx vitest run tests/<Name>.test.tsx`.

Because the directory sits outside `src`, `tsconfig.app.json` includes `["src", "tests"]` — dropping `tests` there would silently exclude every test file from type checking, which is what catches a fixture left stale by a contract change. Tests import the subject through the `@/` alias like any other module (`import Sync from '@/pages/Sync'`); there are no relative `./` imports into `src`.

There is no Vitest config block and no setup file. Vitest reads `vite.config.ts` directly, so the React plugin and the `@/` alias already apply. A test file opts into a DOM by declaring `// @vitest-environment jsdom` on its first line rather than configuring a global environment, and imports `describe`/`it`/`expect`/`vi` from `vitest` explicitly rather than enabling `globals`. Without `globals`, Testing Library's automatic cleanup is not registered either — each test file calls `cleanup()` in its own `afterEach`.

The suite is `tests/AsyncCard.test.tsx`, `tests/Home.test.tsx`, `tests/Sync.test.tsx`, and `tests/Analytics.test.tsx`.

`tests/AsyncCard.test.tsx` covers the composition itself, with no API mocking: the shell and state region are different DOM elements and the region is the shell's child; a `variant="table"` shell is a wrapper around the `<table>`, never the table itself; a `variant="plain"` shell stays the same node across all three of its states and each of those states carries `.card` while the error also keeps `.async-card-error`; the loading region is a `role="status"` carrying readable copy beside an `aria-hidden` spinner; loading takes precedence over both a stale error and an empty result; a resolved error wins over an empty message; and `rerender` proves the **same** shell node carries the transition in both directions — indicator to content, and content back to indicator on a refetch.

`tests/Home.test.tsx` gives each of the four Dashboard requests its own deferred promise, so a test controls exactly when each lands. It asserts four shells and four indicators before anything resolves, that the three static navigation cards are not loading surfaces, that resolving one request populates its card while the other three still show indicators, that an empty message appears only after that request finished, and that a rejected request's `role="alert"` lands inside its own card's shell. Cards are located by heading text through `closest('.async-card')`, and the node is compared across the transition rather than re-queried by class alone.

`tests/Sync.test.tsx` covers the History tab end to end. It mocks `@/api` wholesale with `vi.mock` and renders the page inside a `MemoryRouter` with an `initialEntries` route, which is how URL-param behavior (`tab`, `history_page`) is exercised. Assertions use `toHaveProperty('disabled', …)` rather than jest-dom matchers, since `@testing-library/jest-dom` is deliberately not installed. Timestamp assertions go through a `localTime()` helper that formats the expected value with the same `toLocaleString()` the component uses, so the suite does not depend on the runner's locale or timezone. A `LocationProbe` component (`useLocation()`, rendered alongside the page and exposed off `renderSync()` as `getSearch()`) lets its `tab selection and URL state` tests assert on the parsed query string itself — the default-tab normalization on bare entry, that it preserves unrelated params, and that switching back to Sync sets `tab=sync` explicitly rather than deleting it — without depending on serialized param order.

`tests/Analytics.test.tsx` isolates the page's URL/tab routing behavior from its many request-backed child surfaces: it mocks `@/api` wholesale (including the endpoints `CommentsPanel` and `PeriodSelect` call), stubs `ResizeObserver` (unavailable in jsdom, needed by `AnalyticsChart`/`TrafficSourceChart`), and reuses the same `LocationProbe`/`MemoryRouter`/`getSearch()` pattern as `Sync.test.tsx`. Its `tab selection and URL state` tests assert that a bare `/analytics` gains `tab=analytics`, that unrelated query params survive that normalization, that an explicit non-default tab (e.g. `comments`) is left alone rather than duplicated or overwritten, and that every tab switch (`analytics` / `traffic-sources` / `comments`) leaves the corresponding value explicit in the URL.

History fixtures are built by a `run()` factory and a `batch()` factory that sums its children's counters the way the backend does, keeping a fixture from asserting a rollup the real contract could not produce. Because an expanded batch puts a second `<table>` in the document, tests scope queries with `within(parentTable())` / `within(nestedTable())` rather than bare `getAllByRole`, and count `screen.getAllByRole('table')` to assert expansion state. Its history-state tests also hold `getSyncRuns()` deferred to assert the table card's shell and indicator before resolution, then that the same shell node holds the table afterwards with no indicator left, and that a rejected request's alert stays inside that same shell. Three further tests pin the derived pending state: a direct History URL renders neither empty message on its first frame; clicking Next drops the previous page's rows immediately rather than holding them under the new request; and reopening the tab shows the indicator instead of cached rows. Each fails against a loading flag set inside the effect.

CSS is not applied in this environment — Vite stubs stylesheet imports under Vitest — so layout rules (the flex/grid fill rules for state regions, the table shell's border transfer) are not covered by tests and need the manual pass.

## Compatibility conventions

- `@/` alias maps to `src/`, configured in both `vite.config.ts` (`resolve.alias`) and `tsconfig.app.json` — a path change must be kept in sync across both files or the build and the editor's type-checking will disagree.
- Adding a new sortable column anywhere requires updating the frontend's `SortKey` union *and* the backend's `_..._SORT_COLUMNS` allow-list (see `api.md`/`database.md`) — the two are not generated from a shared source.
- `Home.tsx`'s locally-duplicated `toTopVideoShape`/date-window logic (see `lib/topVideos.ts` above) means a fix or change to the shared versions in `lib/topVideos.ts` or `PeriodSelect.tsx` will not automatically propagate to `Home.tsx` — check it explicitly when touching either shared helper.
