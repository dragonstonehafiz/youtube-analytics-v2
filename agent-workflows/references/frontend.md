## API client (`src/api.ts`)

Thin `fetch` wrappers, one per backend route (see `api.md` for what each endpoint does). All go through `buildUrl(path, params?)`, which sets a query param only when its value is truthy — an empty string or `undefined` is simply omitted, not sent as `key=`.

Notable naming quirks (source of truth is the function body, not the name):

- `triggerSync(plan)`, `getSyncStatus()`, and `getSyncRuns(page, pageSize)` are the wrappers that do **not** follow the file's `fetch(...).then(r => r.json())` shape — each checks `response.ok` before parsing a body. `triggerSync(plan)` POSTs a JSON `SyncPlan` body with an explicit `Content-Type` and rejects with an `Error` built by `syncErrorMessage(response)` — which reads FastAPI's `detail` field as either a plain string (400/409) or the first entry's `msg` from a 422 validation array, falling back to the status code. `getSyncStatus()` rejects with a plain `Error` naming the status code on any non-2xx response, so an unreachable or erroring `/sync/status` never gets silently parsed into a fabricated idle-like object. `getSyncRuns(page, pageSize)` sends the snake_case `page`/`page_size` params and rejects with the fixed `Sync history request failed (<status>)` — built from the status code alone, never from the response body, so a backend traceback cannot reach the history UI through an error path. Every other wrapper in the file resolves regardless of status, so a failed request would otherwise surface as a successful parse of an error body.

- `getPlaylistAnalytics(id, params)` and `getPlaylistAggregatedAnalytics(id, params)` are identical — both hit `GET /analytics/playlists/{id}`. Only `getPlaylistAnalytics` is actually called (from `PlaylistAnalytics.tsx`).
- Functions taking a generic `params?: Record<string, string>` bag (`getChannelAnalytics`, `getPlaylistAnalytics`, `getChannelTrafficSources`, `getPlaylistTrafficSources`, `getTopVideosByTrafficSource`, `getPlaylistTopVideosByTrafficSource`) differ stylistically from the rest of the file, which take named positional params — both patterns exist side by side; there is no in-progress migration between them documented anywhere.
- `getTopVideosByViews(sortBy, startDate?, endDate?, contentType?, privacyStatus?, title?)` and `getPlaylistTopVideosByViews(id, sortBy, startDate?, endDate?, contentType?, privacyStatus?, title?)` take a required `TopVideoSortBy` (`'views' | 'watch_time'`) as their first optional-adjacent argument, positioned before the date/filter params. There is no default — every repository call site must pass one explicitly, so `tsc` catches an omitted sort rather than it silently defaulting. All 8 current call sites are accounted for: 6 pass the literal `'views'` (`Home.tsx` ×2, `Analytics.tsx`/`PlaylistAnalytics.tsx` seven-day sidebar effects ×2 each), 2 pass the URL-derived `topVideosSortBy` (the main `TopVideosList`-feeding effect in `Analytics.tsx` and `PlaylistAnalytics.tsx`, which can resolve to either `'views'` or `'watch_time'` depending on the `top_videos_sort_by` param). Only the main `TopVideosList`-feeding call sites pass the trailing `title` argument — the seven-day sidebar effects and `Home.tsx` omit it, keeping those datasets independent of any page filter.
- `getVideosPublished(startDate?, endDate?, contentType?, privacyStatus?, playlistId?, title?)` likewise takes `title` as a trailing optional argument, added after `playlistId`.
- `getComments(query?)`, `getVideoComments(id, query?)`, and `getPlaylistComments(id, query?)` take a single optional `CommentQuery` options object (`page`, `pageSize`, `sortBy`, `text`, `videoTitle`, `author`, `startDate`, `endDate`, `contentType`) rather than positional params — a third style in this file, chosen because the endpoints take nine filters. All three delegate to a private `fetchComments()` that checks `response.ok` before parsing, so a 404 from an unknown video or playlist rejects instead of resolving into an object with no `items`. `commentParams()` maps the camelCase options onto the snake_case query names.

## Shared libraries (`src/lib/`)

**`trafficSources.ts`**
- `formatTrafficSource(type)` — raw API enum → human label (e.g. `YT_SEARCH` → "YouTube Search"); falls back to a generic title-cased version of the raw string for unmapped types.
- `getTrafficSourceColor(type)` — fixed `Record<type, hex>` lookup of 16 explicit colors; every traffic source type keeps the same color everywhere it's rendered (table bars, chart lines, donut slices), regardless of its rank in any particular filtered view. Falls back to `TRAFFIC_SOURCE_OTHER_COLOR` (grey, `#898781`) for unmapped types.
- `aggregateTrafficSourceTotals(rows)` — sums `views`/`watch_time_minutes` per traffic source type across all rows, sorted by views descending.

**`topVideos.ts`**
- `toTopVideoShape(video: Video): TopVideo` — maps a lifetime `Video` record into the `TopVideo` shape used by ranked/carousel components (`period_views = view_count`, `period_watch_time_hours = total_watch_time_hours`, `period_earnings_sgd = total_revenue_sgd`).
- `last7Dates()` — `[start, end]` ISO dates for the rolling last-7-days window (inclusive of today).
- Used by `Analytics.tsx` and `PlaylistAnalytics.tsx`. `Home.tsx` does not import this module — it defines its own local, functionally-identical copies of both `toTopVideoShape` and a `last28Dates`-equivalent inline instead. If `topVideos.ts` or `PeriodSelect.tsx`'s date helpers change, `Home.tsx`'s inline copies won't pick up the change automatically.

## Shared components (`src/components/`)

|---|---|
| `TopNav.tsx` | Sticky nav: Videos, Playlists, Analytics, Comments, Sync. No "Home" link — the "YouTube Analytics" brand text is itself a `<button>` navigating to `/`. Back arrow shown only on detail pages (`/analytics/videos/:id`, `/analytics/playlists/:id`, matched via regex `^\/analytics\/(videos\|playlists)\/`), which still covers the scoped Comments tabs since those stay under `/analytics/...`. Comments is not a route — it targets `/analytics?tab=comments`. Because it shares the `/analytics` pathname with the Analytics item, `isLinkActive()` decides between them on the `tab` param: Comments is active on any `/analytics` path with `tab=comments`, Analytics on any other `/analytics` path; every other link still prefix-matches the pathname. A click on an already-active link is a no-op (no navigation, no history change, current query state untouched) — which is also what keeps clicking Videos from wiping that page's filters; otherwise it calls plain `navigate(to)`, pushing a history entry. `SyncStatus` renders in the right side of the nav on every page. |
| `CommentsPanel.tsx` | Self-contained Comments tab used by all three Analytics pages — the one component in the codebase that fetches its own data, since the three hosts share no comment state to hand down. Takes a single discriminated-union `scope` prop (`{kind:'channel'}` / `{kind:'video',videoId}` / `{kind:'playlist',playlistId}`) and calls the matching endpoint. Owns its filter bar (From → To \| Comment \| Commenter \| Video \| Type \| Sort), loading/error/empty states, and pagination (`PAGE_SIZE = 25`). Renders a **feed, not a table** — the one data surface in the app that isn't an HTML `<table>`, because a comment body is prose of arbitrary length that a `table-layout: fixed` cell either truncates or stretches. Outside a video scope the page's comments are grouped into one shared `.card` per video, headed by its thumbnail, title (linking to that video's own Comments tab), and comment count; a video scope renders a single `.card` holding the list. An in-flight request is discarded when the scope or a filter changes, so a stale response can't land after a newer one. |

Returns `null` until the first poll resolves and status is not yet unavailable. It holds **no** manual sync controls — triggering a sync lives on the `/sync` page. The `sync-pulse` keyframes it animates with are defined once in `index.css`; `Sync.css` does not use them. |
| `PeriodSelect.tsx` | Shared quick-select: Custom (clears dates — no filter) / Last 365 days / Last 90 days / Last 28 days / then years from earliest `published_at` down to current year (via `/meta/date-range`). Exports `last365Dates()`, `last90Dates()`, `last28Dates()`. Component default is Custom; pages wanting a non-Custom default set their own initial URL param state. |

## Pages

**`Home.tsx`** — 3-card nav grid (Videos/Playlists/Analytics) plus a 3-column `.home-carousels` grid: "Top Videos (Last 28 Days)" and "Top Shorts (Last 28 Days)" via `getTopVideosByViews('views', ...last28Dates(), 'video'|'short', 'public')`, "Latest Uploads" via `getVideos(1, 10, 'published_at', 'desc', ..., 'public')` (no content-type filter, so mixes videos/shorts) mapped into `TopVideo` shape via a **locally-defined** `toTopVideoShape()` (see the `lib/topVideos.ts` note above), and a `TrafficSourceDonutCard` ("Traffic Sources (Last 28 Days)") which wraps to its own row since the grid stays 3 columns. All four always public-only, independent of any page filter — Home has no filter bar.

**`Videos.tsx`** — Paginated, server-side sorted/filtered table via `VideoTable`. URL params: `page`, `sort_by`, `sort_dir`, `title`, `start_date`, `end_date`, `content_type`, `privacy_status`. Page size 25 (`VideoTable.PAGE_SIZE`). Only `initialLoading` shows a spinner — subsequent page/sort/filter changes swap rows in place. `VideoStatsBar` rendered above `VideoTable`, fetched separately with the same `start_date`/`end_date` values, but each endpoint applies them to a different column: `getVideos()` filters table rows by `videos.published_at`, while `getVideoStats()` uses the same two dates as the Legacy/New publication split *and* the `video_analytics.date` window for period views/earnings (see `database.md`).

**`Playlists.tsx`** — Same pagination/sort/URL-param pattern, implemented as its own inline table (does not reuse `VideoTable`, since that component is video-row-shaped). Filter bar has title search only — no date or type filter. Sortable columns: `last_item_added` (default desc), `published_at`, `item_count`, `total_views`, `total_earnings_sgd`. Column order: Thumbnail \| Title \| Last Added \| Created \| Views \| Earnings (SGD) \| Videos.

**`Sync.tsx`** — Two tabs driven by a `tab` URL param: **Sync** (default) and **History**. Anything other than the literal `'history'` — including an absent or unrecognized value — resolves to Sync, so `/sync` stays the canonical default URL. `handleTabChange` sets `tab` only when leaving the default and deletes it otherwise; it never touches `history_page`, so a non-default history page survives a round trip through the Sync tab.

The Sync tab holds the manual sync form; it is the only place a sync can be triggered. A `.data-table.sync-table` with three columns (Include \| Stage \| Period) renders one row per stage from a module-level `STAGE_ROWS` constant in canonical order: `playlists`, `videos`, `comments`, `pruning`, `video_analytics`, `video_traffic_sources`, `fx_rates`. All checkboxes start checked **except `pruning`**, which starts deselected every time the component initializes (`ALL_INCLUDED.pruning = false`) — pruning deletes video rows and must be opted into deliberately. Every selector starts at "New data only". `videos`/`playlists`/`pruning`/`fx_rates` show a plain "Not applicable" in the Period column; `video_analytics`/`video_traffic_sources` each get an independent `StagePeriodSelect` (New data only \| Full history \| then each year from the current year back down to `/meta/date-range`'s `earliest_year`); `comments` gets a `StageScopeSelect` offering exactly two options, Incremental (`scope="incremental"`) and All (`scope="all"`) — labelled with the scope values themselves rather than the period selector's date-range wording, and with no year, since the backend rejects one there. `toggleStage()` links pruning to its prerequisites in both directions: checking `pruning` also checks `playlists` and `videos` in the same update; unchecking either `playlists` or `videos` also unchecks `pruning` — so the UI can never submit a plan the backend would reject for a missing prerequisite. Unchecking any other stage disables its selector but **keeps** the selection, so rechecking restores it. State is local component state, not URL params — the plan is an ephemeral action, not a shareable filter (contrast [URL and filter state](#url-and-filter-state)). Does not reuse `PeriodSelect.tsx`, whose date-range semantics don't match sync scopes.

Polls `/sync/status` every 5s into `status: SyncStatusResponse | null`, tracking poll/refresh failures in a separate `statusUnavailable` flag rather than overwriting the last-known `status`. Polling exists **only** to protect the form: `awaitingFirstStatus` (`status === null`) and `statusUnavailable` feed into `locked` alongside `state === 'running'` and `submitting`, and `locked` is wired to the `disabled` attribute of every checkbox, selector, and the submit button. None of those states render any page-level text — there is no status banner and no terminal success/failure block, and the submit button's label is the fixed string `Sync selected` in every state. `disabled` is the only button-level lifecycle signal. All visible lifecycle feedback — the running progress message, terminal messages, and the "Status unavailable" pill — belongs to the navbar's `SyncStatus` component (`components/SyncStatus.tsx`, `.sync-status*` classes in its own `SyncStatus.css`), which is unrelated to this page and unchanged. `handleSubmit` keeps the queue-request error path (`.sync-error`, "Could not start sync"-style, from `triggerSync()` rejecting) separate from the immediate post-queue status refresh: that refresh's own failure only sets `statusUnavailable` and never populates `.sync-error`, so a successful queue submission followed by a failed refresh cannot be mistaken for a failed sync start. The full-width "Sync selected" button is disabled whenever `locked` is true or nothing is selected — the backend still rejects empty and racing submissions authoritatively.

`StagePeriodSelect` and `StageScopeSelect` are extracted as their own components purely for type safety: a type predicate cannot keep a stage narrowed to `PeriodAwareSyncStage`/`ScopeAwareSyncStage` inside a nested `onChange` arrow, so the narrowed value is passed as a prop instead.

The History tab renders server-paginated sync-stage runs, newest first, via `getSyncRuns(page, HISTORY_PAGE_SIZE)` with `HISTORY_PAGE_SIZE = 25`. It fetches only while its own tab is active — entering the tab, changing page, or reloading fetches; there is no auto-refresh while it stays open. Its request state (`historyItems`, `historyTotal`, `historyLoading`, `historyError`) is entirely separate from the form's `status`/`statusUnavailable`/`submitting`/`error`, so a history failure can never disable or alter the manual workflow, and vice versa. The effect's cleanup flips an `active` flag so a superseded response is discarded rather than overwriting the page the user has since moved to. Loading (`.loading`), request error (`.sync-error`), empty (`.sync-history-empty`), and populated are mutually exclusive branches; pagination controls render only in the populated branch, including for a single page where both buttons are disabled.

Eight columns — Stage \| Scope \| Status \| Started \| Completed \| Fetched \| Written \| Deleted — built from an **explicit** field list, never a spread of the run object. `sync_runs.error_message` reaches the client in the API contract but is deliberately never rendered, not even for a failed row, and neither are `id` or `batch_id`; `Sync.test.tsx` asserts sentinel values for both never appear in the document. `stageLabel()` maps `sync_type` through the same `STAGE_ROWS` labels the form uses and falls back to the raw stored value for a stage the UI no longer offers. `scopeLabel()` prefers a non-null `year`, else labels the stored scope Incremental/All, else the shared `EMPTY_CELL` em dash. `formatTimestamp()` renders stored UTC ISO strings in the browser's locale via `toLocaleString()` and returns the em dash for a null or unparseable value — a still-running row legitimately has `completed_at = null`.

## URL and filter state

- Filter state lives in URL search params on every page, never component state — filters survive reloads/back-forward navigation and are shareable links.
- On `Videos.tsx` and `PlaylistAnalytics.tsx`'s Videos tab, the default for `start_date`/`end_date` is `''` — an absent param and an explicit empty string mean the same thing ("all data"), so there's no ambiguity to handle.
- On `Analytics.tsx`, `VideoAnalytics.tsx`, and `PlaylistAnalytics.tsx`'s Analytics/Traffic-Sources tabs, the default is **Last 28 days** instead — which makes an *absent* param mean something different from an *explicit empty string* (Custom/all data). Reading these must use `searchParams.has(key)` to distinguish the two states, and any handler writing an empty date must call `.set(key, '')` rather than `.delete(key)` — otherwise selecting "Custom" immediately snaps back to Last 28 days on the next render.
- Filter bar order is consistent everywhere it appears: Period → From/Start → To/End \| Title (where present) \| Type (where present) \| Privacy (where present), with `.filter-bar-sep` dividers between logical groups. No Apply button anywhere — every filter change triggers a live fetch. `CommentsPanel`'s bar follows the same shape with comment-specific fields: From → To \| Comment \| Commenter \| Video \| Type \| Sort.
- `CommentsPanel`'s own state is prefixed `comments_` (`comments_page`, `comments_text`, `comments_video_title`, `comments_author`, `comments_start_date`, `comments_end_date`, `comments_content_type`, `comments_sort_by`) so it can share an Analytics URL with the Analytics, Traffic Sources, and Videos tabs without either clobbering the other's filters — the same collision-avoidance reason `PlaylistAnalytics.tsx` prefixes `analytics_*`. Its dates default to empty (all data), so unlike the Analytics tabs it needs no `.has()`/`.set('')` distinction. Any filter or sort change deletes `comments_page` rather than setting it to 1, and page 1 is likewise represented by the param's absence.
- `Sync.tsx` is query-driven for navigation state only: `tab` (`history`; absent or unrecognized means the default Sync tab) and `history_page` (page 1 is the param's absence, matching `CommentsPanel`'s `comments_page`). Its stage/period selections stay in component state deliberately — the plan is a one-shot action, not a shareable filter, and switching tabs does not reset it. `history_page` is parsed through a `parsePage()` guard that accepts only finite integers ≥ 1, so a hand-edited `0`, `-2`, `1.5`, or `abc` falls back to page 1 rather than producing `NaN` or a negative offset. A page past the end returns no items, and the empty branch keys on `historyItems.length === 0` alone rather than on `historyTotal` — so it renders "No sync runs recorded." with **no** pagination controls, even when `total > 0` and earlier pages do hold runs. There is no invalid Next action to click, but the copy overstates the case: it reads as "history is empty" when it means "this page is". Reachable only by hand-editing the URL, since Next disables at the last page.
- Every query-driven page uses `useReplaceSearchParams()` (`src/hooks/useReplaceSearchParams.ts`) instead of React Router's `useSearchParams()` directly. It wraps the same `[searchParams, setSearchParams]` pair but forces every update to `{ replace: true }`, so filter/sort/page/tab changes update the URL without growing browser history — the current pathname keeps a single history entry no matter how many query changes happen on it. Pathname navigation (`<Link>`, `TopNav`'s `navigate(to)`) is unrelated to this hook and continues to push history normally. Any new query-driven page must use this hook rather than calling `useSearchParams()` directly.

## Tests

Component tests run on Vitest with `@testing-library/react` and `jsdom`, all three development-only dependencies. `npm test` (`vitest run`) runs the suite; a single file runs via `npx vitest run src/pages/<Name>.test.tsx`.

There is no Vitest config block and no setup file. Vitest reads `vite.config.ts` directly, so the React plugin and the `@/` alias already apply. A test file opts into a DOM by declaring `// @vitest-environment jsdom` on its first line rather than configuring a global environment, and imports `describe`/`it`/`expect`/`vi` from `vitest` explicitly rather than enabling `globals`. Without `globals`, Testing Library's automatic cleanup is not registered either — each test file calls `cleanup()` in its own `afterEach`.

`src/pages/Sync.test.tsx` is the current suite. It mocks `@/api` wholesale with `vi.mock` and renders the page inside a `MemoryRouter` with an `initialEntries` route, which is how URL-param behavior (`tab`, `history_page`) is exercised. Assertions use `toHaveProperty('disabled', …)` rather than jest-dom matchers, since `@testing-library/jest-dom` is deliberately not installed. Timestamp assertions go through `toLocaleString()` on the expected value too, so the suite does not depend on the runner's locale or timezone.

## Compatibility conventions

- `@/` alias maps to `src/`, configured in both `vite.config.ts` (`resolve.alias`) and `tsconfig.app.json` — a path change must be kept in sync across both files or the build and the editor's type-checking will disagree.
- Adding a new sortable column anywhere requires updating the frontend's `SortKey` union *and* the backend's `_..._SORT_COLUMNS` allow-list (see `api.md`/`database.md`) — the two are not generated from a shared source.
- `Home.tsx`'s locally-duplicated `toTopVideoShape`/date-window logic (see `lib/topVideos.ts` above) means a fix or change to the shared versions in `lib/topVideos.ts` or `PeriodSelect.tsx` will not automatically propagate to `Home.tsx` — check it explicitly when touching either shared helper.
