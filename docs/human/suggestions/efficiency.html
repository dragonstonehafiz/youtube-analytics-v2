Backend: sync

One connection and commit per row

per row

Each upsert opens a new SQLite connection, runs three PRAGMA statements, writes one row, and commits.

Where
upsert_video_analytics, upsert_video_traffic_source, upsert_playlist_item, upsert_own_video, upsert_comment_author + upsert_comment (two per comment), called in loops from sync/stages.py
Cost
A commit per row instead of per batch. The analytics stages run on concurrent workers, so each commit also waits for SQLite's single write lock.

Full video lookup inside every per-video loop

per video × 5 stages

Stages fetch the owned ID list, then call get_owned_video(id) once per video just to read its title and publish date (sync_comments reads only the title).

Where
sync_video_analytics, sync_video_traffic_sources, sync_search_insights, sync_related_video_insights, sync_comments
Cost
One query per video, and get_owned_video also sums lifetime revenue and watch time over all of that video's analytics rows, which the stages never use. Each sum is an indexed scan of one video's rows, so the time is likely small next to the YouTube API calls made for the same video.

Connections closed by garbage collection

every DB call

with get_connection() as conn commits or rolls back on exit but does not close the connection.

Where
Every function in backend/database/; nothing calls close()
Cost
Closing depends on the connection object being freed, not on the with block ending.

Backend: API reads

Lifetime earnings recomputed on every read

per request

Lifetime SGD earnings are not stored. Each list, detail and existence check sums every daily analytics row × that day's FX rate again.

Where
get_all_videos and get_owned_video in database/videos.py; get_all_playlists, get_playlist and get_playlist_videos in database/playlists.py. get_owned_video is also the 404 check for single-video routes, and get_playlist for the playlist videos and playlist comments routes.
Cost
Work proportional to all analytics rows of the videos involved, on every request, for totals that change only after a sync. get_all_videos does it for every matching video before applying LIMIT, even when sorting by publish date.

Playlist list runs its aggregate twice

per request

get_all_playlists runs the full grouped query once inside COUNT(*) and again for the page.

Where
database/playlists.py, behind GET /playlists
Cost
Every join and subquery in that query runs twice per request.

Playlist lookup repeated per endpoint

per request

The playlist statistics route and each playlist analytics route check the playlist exists and load its video IDs before their own query.

Where
resolve_playlist_video_ids (routes/video_scope.py), called by the 9 playlist routes in routes/analytics.py and the statistics route in routes/playlists.py
Cost
Two extra queries per request. The existence check (playlist_exists) is a single-row lookup with no totals. PlaylistAnalytics sends many of these requests together, each repeating both lookups.

Substring title search

per filtered request

The title filter is v.title LIKE '%…%' OR v.id LIKE '%…%'.

Where
11 query functions in backend/database/
Cost
A leading % cannot use an index, so every video row is scanned. Small at the current table size.

Frontend

Two status pollers on the Sync page

every 5 s

The top navigation and the Sync page each request /sync/status every 5 seconds.

Where
components/SyncStatus.tsx, pages/Sync.tsx
Cost
Two requests per interval on Sync; the top navigation's poll runs on every page whether or not a sync is running.

Superseded requests are not cancelled

per filter change

Old responses are ignored through an active flag, but no request is aborted.

Where
Every data effect; there is no AbortController in frontend/src
Cost
Each filter, date or tab change leaves the previous requests running to completion on the backend.

Term videos load twice

per filter change

A date, title or privacy change sends the “videos for the top search term” requests straight away with the old top term, then again when the new term lists arrive.

Where
Analytics, PlaylistAnalytics
Cost
Two extra requests per change, even when the top term hasn't changed.

Hidden-tab requests

per page open

Everything except the Related Videos requests loads whichever tab is open.

Where
Analytics and PlaylistAnalytics (opening on Comments still sends 13 analytics requests); VideoAnalytics loads its chart, traffic and search requests on every tab
Cost
Requests for data that is not on screen.

Date range on every appearance

per appearance

The period dropdown requests /meta/date-range each time it mounts.

Where
PeriodSelect (switching tabs brings it back; PlaylistAnalytics has two), plus a separate request in Sync
Cost
The same value fetched repeatedly.
