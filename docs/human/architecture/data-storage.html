Data storage and access

This page shows where the data lives, how the backend reads it into Python objects, writes those objects back and deletes rows, and how read results become the JSON the frontend receives.

Source revision b2d6118

Storage

Everything is in one SQLite file, backend/data/youtube.db. backend/schema.sql defines its 12 tables and runs on every startup, creating only tables that are missing.

Which table references which

Each arrow starts at a table that stores another row's ID and points at the table that ID belongs to. The label on the arrow is the column holding the ID.

Declared foreign keys

Deleting a video cascades to its analytics, traffic sources, search terms, related-video rows (as target), comments, and coverage. Deleting a playlist cascades to its items. A comment author cannot be deleted while a comment still uses it.

Links without a foreign key

playlist_items.video_id can name a video that isn't stored. related_videos.referrer_video_id can name another channel's video with no row at all. Queries join these with LEFT JOIN or filter them out; the schema never checks them.

Owned vs external videos

videos.own is 1 for this channel's uploads and 0 for another channel's video stored only as a Related Video referrer. Every catalog and analytics read requires own = 1.

Row objects

Each table has one plain Python data class in backend/database/dataclasses/. Its fields are the table's columns in the same order, and every field defaults to None, because a read may select only some columns. The classes only hold values. The two things they can do are turn themselves into a dictionary with to_dict() and be built from one with from_dict(). They cannot run a query and know nothing about tables or connections.

None means either "stored as NULL" or "not selected". The caller knows which fields it asked for, so it only reads those. Zero, False and empty strings are never turned into None.

Dates and timestamps stay as the stored text. The only converted column is Video.own, which becomes True or False, or stays None when it wasn't selected or a LEFT JOIN found no video.

How the reader and writer find a table

backend/database/tables.py holds explicit lists pairing each row class with its table and with the columns that identify one row. The reader and the writer both use them, and a class name is never used to guess a table name.

TABLES = {Video: "videos", VideoAnalytics: "video_analytics", ..., SyncRun: "sync_runs"}
KEYS = {Video: ("id",), VideoAnalytics: ("video_id", "date"), ..., SyncRun: ("id",)}
Caller asksselect(Video, ("id", "title"), where=[("own", "=", True)])
TableTABLES[Video] → videos; an unlisted class is an error
Check namesid, title, own must be fields of Video; the operator must be one of = != < <= > >= LIKE IN or NOT IN
Bind valuesSELECT "id", "title" FROM videos WHERE videos."own" = ? with True bound to ?

Column and table names in the SQL come only from these lists and the data class fields; a request string never becomes part of the SQL. Every value, including one with quotes in it, is passed separately as a bound parameter. Tests compare the lists and every class's fields with the real schema, including each table's primary key, so a missing or misspelled column fails the test suite.

One filter for reads and deletes

backend/database/filters.py turns a where list into SQL. reader.select, select_one and scalar use it for reads, and writer.delete uses it for deletes, so the same list matches the same rows in both. Conditions are joined with AND, and every column is written with its table name in front.

where = [("own", "=", True), ("id", "NOT IN", ["v-1", "v-2"])]

reader.select(Video, ("id",), where=where)   # SELECT "id" FROM videos WHERE videos."own" = ? AND videos."id" NOT IN (?, ?)
writer.delete(Video, where=where)            # DELETE FROM videos WHERE videos."own" = ? AND videos."id" NOT IN (?, ?)

NotExists matches rows that no row of another table points at. Each pair names a column of that table and the column of the filtered table it must equal. The subquery gets its own generated name, so a table can even be checked against itself.

Aggregates

Totals such as a search term's views or a video's earnings for a period are not stored in the database. SQLite calculates them each time a request asks, with SUM and GROUP BY, and the result is sent to the frontend in one of two shapes.

Where a calculated total ends up
WhenHeld inSent as JSON
Every result column matches a row class field, e.g. search termsSearchTerm(search_term="cats", views=17){"search_term": "cats", "views": 17}
A total has no matching field, e.g. top videos' period earningsrow[Video] for the video, row.values for period_views, period_earnings_sgd, period_watch_time_hoursThe video's fields and the totals merged into one object: {"id": …, "title": …, "period_views": …, "period_earnings_sgd": …, …}
Search term totals, from the query to the response 
SELECT st.search_term AS search_term, SUM(st.views) AS views
FROM search_terms st JOIN videos v ON v.id = st.video_id
WHERE v.own = 1 AND st.month >= ? AND st.month <= ?
GROUP BY st.search_term
ORDER BY views DESC, st.search_term ASC

terms = reader.fetch(SearchTerm, query)                       # [SearchTerm(search_term="cats", views=17), ...]
items = [term.to_dict(("search_term", "views")) for term in terms]

A SearchTerm built this way is a total across many stored rows, so its video_id, month and updated_at stay None. The route only sends the two fields the query filled.

A few reports finish the calculation in Python after SQLite has added things up: the daily charts fill missing days with zeros, and the traffic-source view keeps the top videos for each source. They return finished dictionaries, which the route sends as they are.

From a stored row to JSON

One video's trip through GET /videos/published, which the charts use to mark upload days.

1 · Stored in SQLite

The full row in videos, all 14 columns.

id='v-1', channel_id='c1', title='Alpha Video', description='', published_at='2024-01-01T00:00:00Z',
duration_seconds=100, thumbnail_url='', content_type='video', privacy_status='public',
view_count=100, like_count=10, comment_count=2, own=1, updated_at='2024-06-01T00:00:00+00:00'

2 · Read into a Video

The route runs the query through the reader. The query selects only the five columns the chart needs, so the other nine fields stay None.

videos = reader.fetch(Video, queries.videos_published(start_date=..., end_date=...))

Video(id="v-1", title="Alpha Video", published_at="2024-01-01T00:00:00Z", thumbnail_url="",
      content_type="video", channel_id=None, description=None, view_count=None, ...)

3 · Turned into a dictionary

The route asks for the same five fields it selected. to_dict() returns a plain Python dictionary with exactly those keys.

items = [video.to_dict(("id", "title", "published_at", "thumbnail_url", "content_type")) for video in videos]

{"id": "v-1", "title": "Alpha Video", "published_at": "2024-01-01T00:00:00Z", "thumbnail_url": "", "content_type": "video"}

4 · Sent to the browser

The route returns {"items": items} and FastAPI encodes it as JSON.

{"items": [{"id": "v-1", "title": "Alpha Video", "published_at": "2024-01-01T00:00:00Z", "thumbnail_url": "", "content_type": "video"}]}

Passing the field list to to_dict() keeps the response to the columns the route read. A listed field that is None is still sent as null, and a name that isn't a field is an error. to_dict() with no list returns every field, so a route uses that form only when it selected every column.

Writing a row

Sync writes every fetched record through backend/database/writer.py. One video's trip from the YouTube API into videos:

1 · Fetched from YouTube

The API client returns a plain dictionary. Its content_type is None because Shorts detection happens later in the stage.

{"id": "v-1", "title": "Alpha Video", "description": "", "view_count": 120, "content_type": None, ...}

2 · Turned into a Video

The stage adds the two fields it decides itself, ownership and the timestamp, and builds the row with from_dict(). An unknown key is an error.

video = Video.from_dict({**video_data, "own": True, "updated_at": now()})

3 · Written

writer.write(video) looks up the key from KEYS, updates the row with that key, and inserts it only if no row matched. Fields that are None are left out of both statements.

UPDATE videos SET "title" = ?, "description" = ?, "view_count" = ?, "own" = MAX("own", ?), "updated_at" = ? WHERE "id" = ?
INSERT INTO videos ("id", "title", ...) VALUES (?, ?, ...)   -- only when the UPDATE matched nothing

Several rows at once

A month of search terms is validated and summed by sync/write_preparation.py, which returns SearchTerm rows without touching the database, then written in one call. The call is all-or-nothing: if any row fails, none of that month is stored.

rows = search_term_rows(video_id, "2024-03", result.terms, updated_at=now())
written = writer.write_many(rows)   # rows processed, added to the stage's rows_written

New rows

A row for a new key needs every column the schema requires. Columns left None get their schema default, such as own = 1 or a comment's like_count = 0. A missing required column fails the write; the writer never makes up a value.

Existing rows

A partial row, such as Video(id="v-1", view_count=7), updates just those columns on a row that already exists, even though it couldn't create one.

Timestamps

The writer never sets updated_at or completed_at. Sync passes now() on every row it writes, so each sync refreshes them even when nothing else changed.

Transactions

Each call opens its own connection, takes SQLite's write lock before deciding between update and insert, commits on success and rolls back on any error. A stage writes each streamed row in its own call, so a failure mid-stage keeps the rows already written.

Deleting rows

Every delete is a call to writer.delete(Model, where=...) from a sync stage. It removes all the matching rows with one DELETE statement and returns how many rows of that table it removed. It uses the same connection and transaction handling as a write.

Videos no longer on the channel

The pruning stage passes the IDs the channel still has. Only owned videos can match, so another channel's video stored as a Related Video referrer is never deleted.

writer.delete(Video, where=[("own", "=", True), ("id", "NOT IN", ["v-1", "v-2"])])

DELETE FROM videos WHERE videos."own" = ? AND videos."id" NOT IN (?, ?)

A condition is required

An empty where list is an error, even on an empty table. There is no call that empties a whole table.

One statement

The matching rows go in one DELETE, never one statement per row. A list too long for SQLite fails and deletes nothing; it is never split, because splitting a NOT IN list would delete rows it meant to keep.

Dependent rows

SQLite removes the rows that depend on a deleted row. The returned count covers only the table named in the call.

Protected rows

Deleting an author that a comment still uses fails, and nothing in that call is deleted.

Who reads and writes the database

Routes and sync don't run SQL themselves. Routes call the reader or a report function; sync calls the reader, the writer, and the sync-run functions.

dataclasses/

One class per table holding a row's values, plus from_dict() and to_dict(). They never run a query or open a connection.

tables.py

The class-to-table list, each table's key columns, and the two write rules: SyncRun ids are generated, and Video.own never goes down.

filters.py

Turns a where list into SQL for reader selects and writer deletes: checks each column and operator, binds every value, and builds NOT EXISTS checks.

reader.py

Every read: select, select_one and scalar for one table, and fetch, fetch_joined and fetch_scalar for SQL from queries.py.

queries.py

10 shared SQL definitions for joined, grouped and ranked reads. Each returns a query that the caller passes to the reader.

writer.py

Every insert, update and delete: write for one row, write_many for a batch of one class, and delete for the rows matching a condition. Only sync calls it.

Report functions

Legacy/New statistics, zero-filled daily charts, top videos per traffic source, referrer totals, and sync-history grouping. The statistics report runs its SQL through the reader; the others open their own connection.

Sync-run log

The sync-run log functions, such as create_sync_run and complete_sync_run, keep their own SQL, each on its own connection.

Database connections

Who opens and closes the SQLite connection
CallWhat happens to the connection
Read without conn=The reader opens one, runs the query, and closes it.
Read with conn=The reader uses it and leaves it open. It never commits or rolls it back.
with reader.connect() as connOpens one connection for several reads, such as a page and its total count, or the four statistics queries, and closes it at the end of the block.
Write or delete without conn=The writer opens one, takes the write lock, commits the whole call or rolls it back, and closes it.
Write or delete with conn=The caller must already be inside a transaction. The writer uses a savepoint, undoes only its own work on an error, and never commits, rolls back or closes the caller's transaction.
