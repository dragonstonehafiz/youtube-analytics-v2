Data storage and access

This page shows where the data lives, how the backend reads it into Python objects, writes those objects back, and how read results become the JSON the frontend receives.

Row objects

Each table has one plain Python data class in backend/database/dataclasses/. Its fields are the table's columns in the same order, and every field defaults to None, because a read may select only some columns. The classes only hold values. The two things they can do are turn themselves into a dictionary with to_dict() and be built from one with from_dict(). They cannot run a query and know nothing about tables or connections.

backend/database/dataclasses/videos.py (abridged) 
@dataclass
class Video(Row):
    id: str | None = None
    channel_id: str | None = None
    title: str | None = None
    description: str | None = None
    published_at: str | None = None
    ...
    view_count: int | None = None
    own: bool | None = None
    updated_at: str | None = None

Video(id="abc", title="Example") is a complete, valid object: id and title hold values and every other attribute is None.

None means either "stored as NULL" or "not selected". The caller knows which fields it asked for, so it only reads those. Zero, False and empty strings are never turned into None.

Dates and timestamps stay as the stored text. The only converted column is Video.own, which becomes True or False, or stays None when it wasn't selected or a LEFT JOIN found no video.

How the reader and writer find a table

backend/database/tables.py holds explicit lists pairing each row class with its table and with the columns that identify one row. The reader and the writer both use them, and a class name is never used to guess a table name.

TABLES = {Video: "videos", VideoAnalytics: "video_analytics", ..., SyncRun: "sync_runs"}
KEYS = {Video: ("id",), VideoAnalytics: ("video_id", "date"), ..., SyncRun: ("id",)}
Caller asksselect(Video, ("id", "title"), where=[("own", "=", True)])
TableTABLES[Video] → videos
Check namesEvery column must be a field of Video
Bind valuesSELECT "id", "title" FROM videos WHERE videos."own" = ?

Column and table names in the SQL come only from these lists and the data class fields; a request string never becomes part of the SQL. Every value, including one with quotes in it, is passed separately as a bound parameter. Tests compare the lists and every class's fields with the real schema, including each table's primary key, so a missing or misspelled column fails the test suite.

One filter for reads, updates and deletes

backend/database/filters.py turns a where list into SQL. reader.select, select_one and scalar use it for reads, and writer.update and writer.delete use it for changes, so the same list matches the same rows in all of them. Conditions are joined with AND, and every column is written with its table name in front.

where = [("own", "=", True), ("id", "NOT IN", ["v-1", "v-2"])]

reader.select(Video, ("id",), where=where)   # SELECT "id" FROM videos WHERE videos."own" = ? AND videos."id" NOT IN (?, ?)
writer.delete(Video, where=where)            # DELETE FROM videos WHERE videos."own" = ? AND videos."id" NOT IN (?, ?)
What each kind of condition becomes
ConditionSQL
("own", "=", True)videos."own" = ?
("published_at", "=", None)videos."published_at" IS NULL — a stored NULL, not a skipped field
("id", "IN", [])0 — matches no row
("id", "NOT IN", [])1 — matches every row; the other conditions still apply
("id", "NOT IN", ["v-1", None])Error: SQL's NOT IN with a NULL in the list would match nothing
("id", "IN", "v-1")Error: a string is not a list of values
NotExists(Comment, (("author_id", "id"),))NOT EXISTS (SELECT 1 FROM comments AS _inner0 WHERE _inner0."author_id" = comment_authors."id")

NotExists matches rows that no row of another table points at. Each pair names a column of that table and the column of the filtered table it must equal. The subquery gets its own generated name, so a table can even be checked against itself.

Aggregates

Totals such as a search term's views or a video's earnings for a period are not stored in the database. Lifetime earnings are the exception: each video and playlist stores its own, updated by the Video Analytics sync. SQLite calculates the other totals each time a request asks, with SUM and GROUP BY, and the result is sent to the frontend in one of two shapes.

Where a calculated total ends up
WhenHeld inSent as JSON
Every result column matches a row class field, e.g. search termsSearchTerm(search_term="cats", views=17){"search_term": "cats", "views": 17}
A total has no matching field, e.g. top videos' period earningsrow[Video] for the video, row.values for period_views, period_earnings_sgd, period_watch_time_hoursThe video's fields and the totals merged into one object: {"id": …, "title": …, "period_views": …, "period_earnings_sgd": …, …}
Search term totals inside traffic.search_terms(), from the query to the result 
SELECT st.search_term AS search_term, SUM(st.views) AS views
FROM search_terms st JOIN videos v ON v.id = st.video_id
WHERE v.own = 1 AND st.month >= ? AND st.month <= ?
GROUP BY st.search_term
ORDER BY views DESC, st.search_term ASC

terms = reader.fetch(SearchTerm, query)                       # [SearchTerm(search_term="cats", views=17), ...]
items = [term.to_dict(("search_term", "views")) for term in terms]

A SearchTerm built this way is a total across many stored rows, so its video_id, month and updated_at stay None. The report returns only the two fields the query filled.

Some reports finish in the reader after SQLite has added things up, still from one query each: the two daily chart reports add a zero row for each day with no stored data, and the traffic-source ranking keeps the top ten videos for each source with reader.group_by().

rows = reader.fetch_joined(query, (VideoTrafficSource, Video))   # inside traffic.top_videos_by_traffic_source()
# ordered by source, then views, highest first
grouped = reader.group_by(rows, (VideoTrafficSource, "traffic_source_type"), limit=10)
# {"SEARCH": [first 10 rows], "SUGGESTED": [...], ...}  — the same row objects, in the same order

SQLite still returns every ranked row; the limit is applied afterwards. The report then returns each bucket's video fields and totals, without the source name, which is already the bucket's key.

From a stored row to JSON

One video's trip through GET /videos/published, which the charts use to mark upload days.

1 · Stored in SQLite

The full row in videos, all 15 columns.

id='v-1', channel_id='c1', title='Alpha Video', description='', published_at='2024-01-01T00:00:00Z',
duration_seconds=100, thumbnail_url='', content_type='video', privacy_status='public',
view_count=100, like_count=10, comment_count=2, own=1, updated_at='2024-06-01T00:00:00+00:00',
total_revenue_sgd=2.7

2 · Read into a Video

The route calls catalog.video_listing() with the five fields the chart needs and no page size. None of them is a calculated total, so the query reads videos alone, with no analytics join, and the other ten fields stay None.

rows = reader.fetch_joined(query, (Video,))

row[Video] == Video(id="v-1", title="Alpha Video", published_at="2024-01-01T00:00:00Z", thumbnail_url="",
      content_type="video", channel_id=None, description=None, view_count=None, ...)

3 · Turned into a dictionary

The report asks for the same five fields it selected. to_dict() returns a plain Python dictionary with exactly those keys.

items = [row[Video].to_dict(("id", "title", "published_at", "thumbnail_url", "content_type")) for row in rows]

{"id": "v-1", "title": "Alpha Video", "published_at": "2024-01-01T00:00:00Z", "thumbnail_url": "", "content_type": "video"}

4 · Sent to the browser

Without a page size the report returns {"items": items} with no count, and FastAPI encodes it as JSON.

{"items": [{"id": "v-1", "title": "Alpha Video", "published_at": "2024-01-01T00:00:00Z", "thumbnail_url": "", "content_type": "video"}]}

Passing the field list to to_dict() keeps the response to the columns the report read. A listed field that is None is still sent as null, and a name that isn't a field is an error. to_dict() with no list returns every field, so a report uses that form only when it selected every column.

Writing a row

Sync writes every fetched record through backend/database/writer.py. It builds a row object from the API data and passes it to writer.write().

writer.write(Video(id="v-1", title="Alpha Video", view_count=120, updated_at=now()))

The writer looks up the table's key in KEYS and uses it to find the row. If a row with that key exists, its columns are updated. If not, a new row is inserted.

UPDATE videos SET "title" = ?, "view_count" = ?, "updated_at" = ? WHERE "id" = ?
INSERT INTO videos ("id", "title", "view_count", "updated_at") VALUES (?, ?, ?, ?)   -- only when the UPDATE matched nothing

Fields that are None are left out of both statements, so an update keeps their stored value and an insert gives them the schema default.

Who reads and writes the database

Routes and sync don't run SQL themselves. Each arrow below is labelled with what the caller uses that part for. Reports run their SQL through the reader, except the storage report, which opens its own read-only apsw connection because it needs SQLite's dbstat table.

dataclasses/

One class per table, holding a row's values.

tables.py

Maps each class to its table and key columns.

filters.py

Turns a where list into SQL.

reader.py

Runs reads and returns data classes. Only the storage report reads around it.

writer.py

Runs every insert, update and delete.

reports/

One file per purpose, such as analytics, traffic, catalog, comments, the Legacy/New statistics, sync history and database storage. Each holds its SQL and returns a finished result.

Sync-run rows

Written through the writer and read back through the reader like any other row.

Database connections

Who opens and closes the SQLite connection
CallWhat happens to the connection
Read without conn=The reader opens one, runs the query, and closes it.
Read with conn=The reader uses it and leaves it open. It never commits or rolls it back.
with reader.connect() as connOpens one connection for several reads, such as a page and its total count, or the four statistics queries, and closes it at the end of the block.
Write, update or delete without conn=The writer opens one, takes the write lock, commits the whole call or rolls it back, and closes it.
Write, update or delete with conn=The caller must already be inside a transaction. The writer uses a savepoint, undoes only its own work on an error, and never commits, rolls back or closes the caller's transaction. A value returned by returning is undone too if the caller later rolls back.
