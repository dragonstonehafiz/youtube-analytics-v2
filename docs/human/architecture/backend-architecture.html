Backend architecture

This page shows what each part of the backend does and how the parts connect.

Source revision b2d6118

What each part does

server.py

Starts the backend: creates the web server, plugs in the API routes, and prepares the database when the app launches.

routes/

The web API. Receives each request from the frontend, checks it, and answers with data from the database. One file per area: videos, playlists, analytics, comments, sync, metadata — plus video_scope.py, which returns 404 for a missing video or playlist and looks up a playlist's videos for the playlist handlers.

database/

The only code that reads or writes SQLite. One small data class per table holds row values; reader.py runs every read and fills those classes; queries.py holds shared SQL for joined and grouped reads; writer.py saves every row sync downloads and deletes the rows sync removes; filters.py turns the conditions for reads and deletes into SQL. The per-domain files hold the sync-run log and the reports that need more than SQL.

sync/

The data importer. When you press Sync selected, it decides what to download, runs the steps in order, tracks progress, and lets you stop it.

youtube/

Talks to Google: signs in with OAuth and calls the YouTube Data and Analytics APIs. Only sync uses it.

logging_config.py

Writes the application and sync log files.

schema.sql

Defines the database tables. Run on every startup, creating only the tables that are missing.

scripts/

One-off migrations that bring an older database up to date. Run by hand, never by the app.

How they fit: the frontend calls routes/, which reads from database/. Separately, sync/ pulls data through youtube/ and writes it into database/. Backend reference describes every file individually.

Package dependencies

database/

Imports no other application package — the shared bottom layer.

youtube/

Never touches the database. Only sync/stages.py moves API results into database/.

routes/

Never calls youtube/. Reads through database.reader directly and turns the returned data classes into JSON.

sync/

The only package that calls youtube/, and the only caller of database.writer, including every delete. It turns each fetched dictionary into a row object before writing it. Only routes/ imports it.

Playlist statistics and every playlist-scoped analytics handler call resolve_playlist_video_ids() in routes/video_scope.py. It checks the playlist exists with require_playlist(), loads its video IDs by running queries.playlist_owned_video_ids through the reader, and the handler passes those IDs to the same read the channel-wide handler uses — get_video_stats() for statistics.

Observations

Broad modules

sync/stages.py holds all nine stage implementations plus their shared helpers. database/queries.py holds all 10 shared SQL definitions for routes and sync.

Unused at runtime

start_background_scheduler(), synced_today(), and run_plan().

Re-export files

Three package __init__.py files re-export every public name (database 36, sync 31, youtube 15); routes/__init__.py combines the six routers.
