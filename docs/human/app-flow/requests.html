Reading this map

Source-defined triggers, not network counts. Each row is one call an effect or handler makes when it runs. main.tsx wraps the app in React StrictMode, so in development every mount effect runs, is cleaned up, and runs again — mount requests go out twice there. Responses from the discarded first run are dropped by the effect's active flag where one exists (track(), CommentsPanel, Sync history); the status polls and PeriodSelect have no such flag and set state twice.

Trigger types

  • Mount — runs when the page or component mounts
  • URL — re-runs when a listed query value changes
  • Response — depends on an earlier request's data
  • Visibility — returns early unless a tab shows
  • Poll — setInterval
  • Action — click or submit handler

Debounce

Typed text fields commit to the URL after 300 ms idle (SEARCH_DEBOUNCE_MS); the request follows the URL change.

Concurrency

Requests in one effect start together; effects whose dependencies change in the same render also start together. Nothing waits unless marked Response.

Default dates

On the three Analytics pages a missing start/end date means the last 28 days (last28Dates()); the defaults are not written to the URL.

Requests that may run unnecessarily

Observations from the source, not measured browser traffic.

Hidden-tab requests

On Analytics and PlaylistAnalytics, every effect except the Related Videos ones ignores tab and ts_tab. ?tab=comments still sends the 13 analytics requests next to the comments request; search-insights requests run while any other sub-tab shows; top-by-source (A9/PL11) runs on the Analytics tab; the sidebar and sortable top-videos requests run on Traffic Sources. VideoAnalytics sends VA2–VA4 on every tab, including Comments.

Term videos fire twice

A13/A14 (and PL15/PL16) depend on the filters and the term-list data. A date, title, or privacy change runs them immediately with the previous top term, then again when the new term list lands, even if the top term is unchanged. Home's H6 depends only on the term list and selection, so it runs once per term-list response.

Two status pollers on /sync

SyncStatus and the Sync page each request GET /sync/status every 5 s, so that page sends two per interval. The top-navigation poll runs on every page whether or not a sync is active.

Date range per mount

Every PeriodSelect mount requests GET /meta/date-range; tab switches remount it; PlaylistAnalytics has two instances on different tabs; the Sync page fetches it separately.

No parent-record gating

VideoAnalytics and PlaylistAnalytics start data requests in the same render as the video/playlist lookup, so an unknown ID produces a burst of 404s. VideoAnalytics hides its tabs then, but the requests are already sent.

History reload

The Sync page drops history state when leaving the History tab and re-requests GET /sync/runs on return.

Unused wrappers

getPlaylistAggregatedAnalytics duplicates getPlaylistAnalytics and has no caller. getTopSearchTerms and getPlaylistTopSearchTerms have no caller, so the two …/search-insights/top endpoints are never requested by the frontend.
